# Profile dialog and command plugins — design (one page)

**Serves:** `goal_requirements.md` R1–R9, U1–U5 · **Written:** 2026-11-21, describing the code *as already
built* (before approval; `baseline.md` *Working tree*) · **Reviewed:** 2026-11-21, F1–F12 by a fresh reviewer, answered by the planner (changes C1–C12 go to P1) · **Approved:** see end.

## Interface

- **Identity name (R1).** `renderer/app.js::identityButtonTitle()` → `"<subject lower-case>@github.com"`
  for a GitHub identity, else `displayId`, else "Choose your identity"; `updateIdentityDot` writes it to
  `#identitySetup.title`, which the settings menu's identity item already reads.
- **Floating dialog (R2, R3, U4).** `showSessionEditor` builds a `.session-editor-title` (grip icon
  `fa-grip-vertical` + `.session-editor-heading`: New profile / Edit profile / Copy profile /
  New-session template, from `options.mode`); the layer `.session-editor-overlay.session-editor-floating`
  is transparent with `pointer-events: none`, only the panel takes the pointer. `dragByTitle(panel,
  handle)` moves it with pointer capture; `clampPanel` keeps it ≥ 8 px from the sides and its top 40 px
  on screen. Closes only by OK, Cancel, or Esc in the panel; a second dialog cancels the first.
- **Shell (R4, U5).** `electron/pty-session.js::commandArgs(command, platform, shell)`: `bash zsh fish ksh
  mksh sh dash` → `['-i','-c',cmd]`, on darwin `['-l','-i','-c',cmd]`; any other shell `['-c',cmd]`;
  win32 `['/c',cmd]`. `defaultShell`: `$SHELL`, else `os.userInfo().shell`, else `bash`.
- **Command plugins (R5–R7, U1–U3).** Main: `electron/command-plugins.js` `configure({dataDir})`, `dir()`,
  `list()` → `{dir, displayDir, seeded, choice, files:[{file, source|error}]}`, `save(choice)`; IPC
  `app.commandPlugins.list|save|open` (`electron/main.js`). Renderer: `loadCommandPlugins()` runs each new
  or changed file with `runCommandPluginFile` (`new Function(source)` in try/catch, inside
  `launch.loadingFrom(file, fn)`); `commandPluginShown(Plugin)`; `showPluginsDialog()` (through `showModal`,
  `popupId: 'plugins'`, Save writes the choice). `launch-core.js::register` marks a file's plugins with
  `Plugin.source` and refuses an id taken by a built-in or another file.
- **"+ Add" (R5).** `steps-editor.js::openMenu`: built-ins, `-`, file plugins, `-`, "Plugins…"
  (`fa-puzzle-piece`, `.launch-add-plugins`); `offered()` = addable ∩ `shown`.
- **Placeholders (R8).** `launch-core.js::slugOf`, `profileVars(name)` → `{name, slug, name_can}`,
  `substitute`; `run` fills a copy of each step's config for validate/apply only; `withName(env, name)`;
  `stepsFor` tries `launchName` then `name`; `relaunchFor(session, name, env)` recompiles stored steps
  under a new name (createSession, for copy / Clone / template "#N").
- **Debug server.** `plugins-state` → files, choice, registered, the open dialog's sections and rows.

## Data and state

- `<stableUserData>/plugins/commands/` (`~/.config/ZBTerm/plugins/commands/` on Linux). First `list()`
  with the dir missing: create it, copy `renderer/plugins/samples/*.js`, write
  `commands.json` = `{"commands": ["sample_custom_command.js"]}` (no `builtin` key = every built-in).
  A dir that exists, even empty or without `commands.json`, is never written by `list()`.
- `commands.json` after Save: `{"builtin": [ids] (absent when all ticked), "commands": [files]}`,
  written to a temp file and renamed. Unreadable or missing → every built-in, no file.
- A profile stores its steps with the placeholders as typed, and the `command`/`cwd` compiled with its
  own name. The registry is in-page memory: files are re-read each time the Plugins dialog opens.

## Refuses

- A file > 256 KB, not a regular file, or past the 200th: listed with its reason, not run.
- A syntax error or a throw while running: listed with `"<Error name>: <message>"`, its plugins dropped.
- A file that registers nothing: "It registered no plugin". An id already taken: "The id X is taken by
  a built-in plugin" / "by <file>". A class that does not extend `LaunchPlugin`: refused.
- An unknown placeholder (`{{foo}}`) is left as typed. A command plugin's `static host` functions are
  not run (the main process does not load these files).

## The reference program, step by step

1. App start (main): `configure({dataDir: stableUserData})`; renderer `init` → `loadCommandPlugins()`
   → IPC `list()` seeds on a first start, returns sources → each file runs in the page.
2. The user opens New/Edit: floating panel near its anchor; the user drags the title, clicks the
   terminal, copies, pastes into a field; the dialog stays.
3. "+ Add" → the grouped menu; "Plugins…" → `showPluginsDialog` re-lists the dir, ticks, Save →
   IPC `save` → `commands.json`; the open steps editor `refresh()`es.
4. OK → `compile(steps, withName(env, name))` → `session.create {cwd, command, steps}` → the PTY spawns
   `$SHELL -i -c "<command>"`. Clone/copy/template: `relaunchFor` with the new name.

## Failure scenarios

Written by a reviewer in a fresh context (different model) from `goal_requirements.md` and this page only.
The planner fills the last column; an empty last column blocks approval.

| # | scenario (input, state, host) | requirement at risk | design answer (change made, or `acceptance/<script>.sh` that catches it) |
|---|---|---|---|
| F1 | **Shell injection via placeholders.** Profile named `x"; rm -rf ~; "` or `a $(cmd)` or with a backtick/newline; a step's command template is `tmux new -s {{name}}`. `substitute` pastes the raw name into a shell string run by `$SHELL -i -c`, so the name becomes shell syntax (a copied/imported/shared profile name is untrusted). Even a harmless name with a space ("Work #2": `#` starts a comment in bash) breaks the command. Nothing says `{{name}}` is quoted or that `{{slug}}` is the only shell-safe form. **Severity: high** | R8, R4 | **Design change in P1 (C1).** Today it is unsafe: `run` fills raw text (`launch-core.js:109,388`) and Shell Command passes its text to the shell unquoted (`shell-command.js:38`), so `tmux new -s {{name}}` with `x"; rm -rf ~; "` becomes `tmux new -s x"; rm -rf ~; "`, and that runs `rm -rf ~`. Fields a plugin quotes itself are already safe: cd `quotePath` (`change-directory.js:57`, or a PTY `cwd` that no shell parses), the sample's `quote` (`sample_custom_command.js:50`), tmux (`tmux_session.js:34`) and venv (`python_venv.js:37`). Change: a plugin lists its shell-text fields (`static shellFields = ['command']` on Shell Command), and `run` fills a placeholder there as one word quoted for that scope's shell (`quote(value, scope.shell)`, `launch-core.js:45`). Result: `tmux new -s 'x"; rm -rf ~; "'`; `echo {{name}}` → `echo 'Work #2'`. `{{slug}}` is always `[a-z0-9-]`. A-12. Check: a unit test in `test/command-plugins.test.js`, and an R4 kit correction (a profile named `z; touch "$HOME/PWNED"` with `echo {{name}}`: the file does not appear and the name is printed). |
| F2 | **Malicious or hostile plugin file.** A `.js` dropped into `plugins/commands/` (downloaded "plugin", synced dotfiles, another local user on a shared dir) runs via `new Function` with full renderer rights on every start and on each open of the Plugins dialog, with no consent step. It can read `app.*` IPC, the debug server, session secrets, share keys. Also an infinite loop at load freezes the renderer (U1 try/catch does not catch it, so "keep the app working" fails), and a 256 KB cap does not stop it. Design only proposes a decision "trusted like rc files". **Severity: high** | U1, R6 | **Partly a design change in P1 (C2).** We document it: a command plugin is trusted user code, run with the renderer's rights, like a shell rc file (A-9). Nothing runs code from outside the user's own data dir. A load that never returns is not caught: the renderer hangs, and the user recovers by renaming the file, the same as with a broken rc file. Q-3 asks whether to add a safe-mode start. Change: on POSIX, `list()` (`command-plugins.js:114-121`) refuses a file, or the directory, that is not owned by the user or is writable by group or others, with "Writable by other users" (shown under U1). Check: a unit test (chmod 0666 → error, not run). |
| F3 | **Plugin shadows or hijacks an id.** A file registers an id equal to a built-in ("shell"), or two files compete: which wins depends on load order (directory order, "new or changed" reload). A file edited to claim an id then renamed changes the winner between starts. Profiles saved with that id then run different code than before (U3 keeps "steps that use it" but by id only). A later-loaded file that is refused leaves a profile silently running the other file's plugin. **Severity: high** | U1, U3 | **Holds; one gap goes to P1 (C3).** Built-ins register first (`index.html:3347` loads `launch-core.js` and the built-ins before `app.js:3353`). Files run in name order (`command-plugins.js:114` `.sort()`). A later claim is refused with "taken by a built-in plugin" or "taken by <file>" (`launch-core.js:312`), so the winner is fixed by name, not by timing. A profile launches its stored `cwd`/`command`, not plugin code (`agent_docs/architecture.md`, the launch-plugins bullet), so a different winner changes only what Edit or Copy recompiles. Gap: a refused file that has not changed is not run again when the winner is deleted (`app.js:96` drops gone files after the loop), so it stays refused until a restart. Change: `loadCommandPlugins` re-runs every file that has an error on each load. Check: a unit test (a.js and b.js both claim `x`: b is refused; delete a, reload: b registers). R4 already checks `thief.js`. |
| F4 | **`-i` rc files misbehave.** The user's `.bashrc`/`config.fish`/`.zshrc` prints a banner, runs `fortune`/`neofetch`, prompts ("Start tmux? [y/N]"), calls `exec tmux`/`exec zsh`, or `read`s: the "command" now blocks or its output is mixed into the session; a `.bashrc` with `[ -z "$PS1" ] && return` behaves differently with `-i -c`. `-i -c` without a tty job control prints "cannot set terminal process group / no job control" noise (bash) on some PTYs; `exit` codes change. Non-interactive side effects (history writes, `compinit` slowness, 2 s startup per profile) and the session's own prompt rc running twice. Design A-3 and the Refuses list say nothing about this. **Severity: medium-high** | R4 | **Holds by design (A-3), documented in P2.** `-i` reads exactly the rc file the session's own prompt reads: the shell is the same `shell` (`pty-session.js:29`), and a profile with no command is the interactive prompt. So a banner, a prompt, `exec tmux` or `[ -z "$PS1" ] && return` behave as they do when a new terminal opens; with `-i`, PS1 is set, so such an rc goes on to the aliases. The session is a real PTY with a controlling tty, so there is no job-control noise. Cost: 20 ms with the maintainer's `~/.bashrc` (`baseline.md` *Cost*). A step that ends in `exec "$SHELL"` reads the rc a second time, as a new prompt does. README (P2) says this. Check: an R4 kit correction in P1 (the scratch `~/.bashrc` also echoes a banner; ALIAS-OK, TOOL-OK and the sample's line still appear). |
| F5 | **fish/zsh/ksh differences and shell detection.** `$SHELL` is `/usr/bin/fish` or a path with a version/symlink (`/bin/sh -> dash`, `/usr/local/bin/bash5`, `/opt/homebrew/bin/zsh`, `-zsh` login name): `commandArgs` matches on what: basename or full string? A mismatch silently falls to `-c` (U5) so aliases stop working (R4); a wrong match gives an unknown shell `-i`. `sh`/`dash` take `-i -c` but ignore `ENV` unless set, so aliases still do not work, yet R4 is "met". fish `-c` with bash syntax (`export A=1 && cmd`, `$(...)`, `&&` before fish 3.0) fails where the same profile ran under bash; `$SHELL` unset/stale (user changed shell with `chsh`, still logged in) differs from the shell at the prompt. **Severity: medium** | R4, U5 | **Holds; one gap goes to P1 (C5).** The match is on the basename with a leading `-` stripped (`pty-session.js:99`): `/opt/homebrew/bin/zsh` → zsh and `-zsh` → zsh get `-i`; `/bin/sh -> dash` → `sh` gets `-i`, and dash reads only `$ENV`, as its own prompt does, so "as at the session's prompt" holds. A fish user's command is fish syntax at their prompt too. A stale `$SHELL` is the same one the prompt uses (`pty-session.js:29`). Gap: `bash5` or `zsh-5.9` falls to `-c`. Change: match `^(bash|zsh|fish|ksh|mksh|sh|dash)(-?[0-9.]+)?$`. Check: `test/engine-client-pty.test.js` cases (bash5, zsh-5.9, -zsh, /opt/homebrew/bin/zsh; xonsh keeps `-c` for U5). R9 runs that file. |
| F6 | **Dialog stays open, Esc and keys go to the wrong place.** Focus in terminal, user presses Esc, Ctrl+C, Ctrl+V: U4 says the terminal gets them, but a global keydown handler or the dialog's focus trap/`autofocus` may steal focus back on every re-render (`refresh()`, a steps-editor rebuild, a profile list update) mid-copy; Ctrl+Shift+V/Ctrl+V pastes go into the terminal instead of the focused field if focus was lost; a modal `showModal` (Plugins dialog, F9) opened over the floating editor swallows Esc and cancels the wrong one, and "a second dialog cancels the first" can discard unsaved edits when the user clicks New again. **Severity: medium-high** | U4, R3 | **Keys hold; one gap goes to P1 (C6).** The editor closes only on Esc in its own panel (`app.js:4392`). The layer passes the pointer through, and no handler moves the focus back: `refresh()` runs only after a Plugins Save, and `openMenu` focuses only when the user opens the menu. `R1_dialog_float.sh` proves it: typing and Esc in the terminal, the dialog still open, Ctrl+V into the field. The Plugins dialog's Esc is on its own panel (`app.js:9008`), outside the editor, so it closes only Plugins. Check to add: an R4 kit correction (after Plugins Save and Esc, `.modal.kind == "session-editor"`). Gap: a second open cancels the first and drops its edits (`app.js:4172`). Change (Q-2, recommended default): a dialog with changes stays; the new request focuses it and the status says "Close the open profile dialog first". A dialog without changes is replaced. Check: an R1 kit correction (type in Name, click New: the edited dialog stays with its text). |
| F7 | **Dialog drag and clamp.** Window resized smaller after open, a second monitor unplugged, devicePixelRatio/zoom changed, or a tall dialog (A-7: bottom may run past the edge, so OK/Cancel are unreachable on a small screen with no scroll); `clampPanel` runs only during drag, not on resize, so the dialog can sit fully off screen with no way back except the pointer-less Esc, which only works when focus is inside it. Pointer capture lost on mouse-up outside the window leaves the panel stuck to the pointer. Dragged panel covers the terminal text the user wants to copy, no dock or resize. **Severity: medium** | R2, R3 | **Partly holds; design change in P1 (C7).** An anchored dialog is placed again on every window resize, and a dragged one is clamped (`app.js:4020` → `place(true)` → `clampPanel`, `app.js:3938`); zoom fires `resize` too. Gaps: a centred dialog (`app.js:4447`, no anchor) has no resize listener; the panel has no `max-height` (`index.html:976`), so OK can sit below the window; a drag ends only on `pointerup`/`pointercancel` (`app.js:3969-3973`). Change: the panel always clamps on window resize; `max-height: calc(100vh - 16px); overflow: auto`, and `clampPanel` keeps the whole panel inside (A-7 is now *fully inside*); the drag also ends on `lostpointercapture`. Docking and resizing the dialog are out of scope. Check: an R1 kit correction (after the drag, `win_size 900 480`: the rect is fully inside and OK is visible). |
| F8 | **Multiple windows / sessions.** Two app windows (or two profiles) each load the plugin dir and each hold their own registry and dialog: window A saves `commands.json` while B holds an old `shown` set, so B's "+ Add" is stale until reopened; both write temp+rename, last write wins, and B's Save overwrites A's choice, dropping files A ticked. On the very first run two windows race `list()` seeding: both see the dir missing, one copies samples while the other writes `commands.json`, or a half-seeded dir is then treated as "exists, never written" (U2) and stays without `commands.json`. **Severity: medium-high** | R6, R7, U2 | **Partly holds; design change in P1 (C8).** Every window asks the one main process (`app.commandPlugins.*`, synchronous fs), so windows of one app cannot race. But there is no single-instance lock (`grep requestSingleInstanceLock electron/main.js` finds nothing), so two app processes can race the first seed, and `seed` writes in three steps (`command-plugins.js:42-50`). Change: seed into a sibling temp directory and `rename` it into place; if the target already exists, delete the temp and leave the target alone. After `save`, the main process sends `commandPlugins:changed` to every window (`sendToAll`, `main.js:501`), which re-reads the choice and refreshes any open steps editor. Two Plugins dialogs open at once: the last Save wins (each re-lists when it opens), which is accepted. Check: unit tests (a seed over an existing dir leaves it byte-identical; a seed interrupted after the copy leaves no target). No GUI check for two windows: a gap, named in `acceptance/README.md`. |
| F9 | **commands.json corruption and drift.** File truncated (crash, sync tool), invalid JSON, `commands` a string, entries with `../x.js` or absolute paths, `builtin` lists an id that no longer exists, names a file since deleted, or duplicates. Design says unreadable means "every built-in, no file", so a corrupt file silently re-enables everything and drops the user's choice, and the next Save overwrites the evidence. Path-like entries may read outside the dir. A symlinked `plugins/commands` or `.js` pointing elsewhere (non-regular check passes on the target) escapes the dir. **Severity: medium** | R6, U1, U2 | **Paths hold; corruption is a design change in P1 (C9).** File names are validated: `isPluginFileName` (`command-plugins.js:98`: no `/` or `\\`, ends in `.js`, not a dotfile) drops `../x.js` and absolute paths. `commands.json` only picks among the files `readdirSync` found (`:114`) and never opens a path itself; duplicates are dropped (a `Set`, `:74`); an unknown built-in id or a deleted file does nothing and is gone after the next Save. A symlinked file or dir is followed (`statSync`, `:120`) and accepted as the user's own; the C2 owner check applies to the target. Gap: a corrupt `commands.json` reads as "every built-in, no file" with no notice (`:70`), and Save overwrites it. Change: `list()` returns `choiceError`; the Plugins dialog shows "commands.json could not be read: <reason>"; Save first copies the bad file to `commands.json.bad`. Check: unit tests (truncated JSON → `choiceError`; Save keeps `.bad`; `../x.js` and `/etc/x.js` dropped). |
| F10 | **Seeding edge cases.** First run: dir missing and `~/.config/ZBTerm` read-only or full: `list()` fails half-way, leaving a dir without `commands.json`, so it is never seeded again (U2/A-5) and the user never sees `sample_custom_command.js` in "+ Add" (R5 says by default it appears). Deleted sample then app update: no re-seed (fine) but docs claim samples exist. ## Questions and assumptions

Soft readings, taken without asking, to read back to the user (also in `status--design.md`):

- **A-1** `{{slug}}` is the primary spelling, `{{name_can}}` an alias (the user asked "better name?").
- **A-2** The user's "work-1" is read as "work-2" for "Work #2": the slug keeps the number.
- **A-3** Shell Command runs `-i -c` (interactive, the rc file the session's prompt reads); `-l -i -c` on
  macOS only. Other: a login shell everywhere (`-l`), which on Linux skips `~/.bashrc` for bash.
- **A-4** Three samples: `sample_custom_command.js` (echoes a message with the placeholders),
  `tmux_session.js` (tmux session named `{{slug}}`), `python_venv.js` (activates a venv).
- **A-5** `commands.json` is seeded only when the directory is missing; never added to afterwards.
- **A-6** Unticking a plugin only hides it from "+ Add"; profiles that use it keep and run it (U3).
- **A-7** "Kept inside the window" means fully inside, both ways (changed after review, F7/C7: the
  panel gets `max-height: calc(100vh - 16px)` and scrolls). The as-built code kept only the title row.
- **A-8** The section heading is the platform's real dir, `~`-shortened (`~/.config/ZBTerm/…` on Linux).
- **A-9** (F2) A command plugin is trusted user code, run with the renderer's rights, like a shell
  rc file. A load that never returns hangs the renderer; the fix is to rename the file. Files not owned
  by the user, or writable by others, are refused (C2).
- **A-10** (F10) A plugins directory the user deleted is seeded again on the next start (R7's wording).
- **A-11** (F11) Two names with the same slug share it (and so a tmux session); not prevented.
- **A-12** (F1) In a shell-text field (Shell Command), a placeholder is filled as one word, quoted for
  that shell; the user writes `{{name}}`, not `"{{name}}"`. Other fields are filled raw and quoted by
  their plugin.
- **Q-1** (open, F11) Renaming a profile from its right-click menu leaves the old name in its
  command, and Edit falls back to raw steps. Recommendation (C11, the default P1 builds): the rename
  recompiles the launch with `relaunchFor`. Other option: leave it and document it.
- **Q-2** (open, F6) A second profile dialog opened while one is open with unsaved edits.
  Recommendation (C6, the default): keep the edited one, focus it and say "Close the open profile
  dialog first"; replace one without changes. Others: ask "Discard changes?"; allow several dialogs.
- **Q-3** (open, F2) A way to start with command plugins off, after a file hangs the app.
  Recommendation: none now (renaming the file is the recovery, A-9). Other: a `--no-command-plugins`
  start flag, declared to paparam in `electron/main.js`, which a hang would need.
- **Q-4** (open, F1) The F1 quoting changes what a Shell Command with `{{name}}` runs. Recommendation:
  C1 as written (quoted, safe). Other: allow only `{{slug}}` in shell-text fields and refuse `{{name}}` there.

## Decisions

None taken in planning. Candidate for the user (`docs/decisions.md`, id at landing): command plugins are
the user's own code, run with the renderer's full rights, trusted like their shell rc files.

## Coalescing review (`electron/main.js:346-350`, `:405-449`; renderer `app.js:8336-8362`, `:8549-8551`, `:8976-8997`)

1. **Bug: an invoke answer can overtake queued output.**
   - Where: `electron/main.js:346-350` and `:1626`.
   - `flushSessionData()` runs only before other *events*. `ipcMain.handle('zbterm:invoke')` answers go straight back and are not flushed first.
   - What goes wrong:
     1. Before F3, worker→main pipe order meant output sent before the snapshot reached the renderer before `session.open`'s answer.
     2. `renderLiveFrame` (`renderer/app.js:3916-3939`) then cleared that output and painted the frame, which `buildLiveBootstrap` (`engine/index.js:2512`) fills with every byte emitted so far.
     3. Now, up to 8 ms or 64 KB of earlier output can still be queued in main when the answer arrives. It is then written on top of the frame, so those lines appear twice.
   - The same applies to the other frame-painting invokes: extend, the restored resync at `app.js:5083`, and joined bootstraps.
   - Probe (`/tmp/claude-1000/zbv4/probe/dup.sh`): switch to a session printing 1200 tagged lines at about 400 lines/s, then compare the renderer's in-session count with the engine's `searchBuffer` count.
     - This package: renderer &gt; engine in 2 of 18 trials (1201, 1202).
     - Pre-fix package `/tmp/claude-1000/zbbs/out`, whose code equals `c5d1c87`: 0 of 10 over, but 2 of 10 at 1199.
     - So a pre-existing loss of one line exists independently of F3. The overshoot appears only with batching, which matches this mechanism. The sample is small.
   - Suggested fix: call `flushSessionData()` in the invoke handler before it returns.
2. **Order relative to other events: correct.** Every non-`session:data` event flushes first, including `session:exit`, `engine:restarting` and `engine:error`. A change of session, source or `hd` flushes before the new chunk is queued.
3. **Flush on exit and close: on exit, yes.** On window close or app quit, at most 8 ms of output is dropped. `sendToAll` skips destroyed windows, so nothing throws.
4. **Ack accounting: unchanged.** The joined bytes are the same, the renderer acks `bytes.byteLength` of the concatenation, and the engine's `pendingBytes` drains the same total. Acks arrive at most 8 ms later.
   - Nit: `byteLength || length` counts characters if `data` were ever a string. Today it is always binary.
5. **Timers: no leak.** There is one global queue and one timer, not one per session. Output interleaved between sessions gets no batching (it flushes on every switch), which is no worse than before.
6. **Single small write: one timer.** Delivery takes at most 8 ms plus scheduling. The echo median without a search is 17 ms (15–17 in earlier reports).
7. **Renderer re-scans: correct.**
   - The `inSessionRescanRunning` flag always clears in `finally`: `scanTerminalBuffer` only awaits `setTimeout(0)`, and a scan made stale by a newer token returns `null`.
   - `drawSearchDecorations` returns when `bufferSearch` is null, so a decoration timer still pending after `clearSearch` is harmless.
   - The 100 ms throttle also applies to user scrolling. The comment says "while output scrolls". This is cosmetic.
   - The same-text early return still lets Backspace+0 retype trigger a search (U3 shows 22 searches).
   - Search results: R2, R5, R6, R7 and R11 are all green.
8. **Unit test (item d): one is needed.** The batching logic is private to `main.js` and nothing tests it. A small extracted queue with tests for order versus other events, flush before invoke answers, byte totals and timer reset is cheap. It would have caught item 1.
